# ТЗ: мягкое возобновление M137-5CH при komi=1.5

Дата: 2026-09-27. Проверенная версия кода: `3e40e541c6717fb2eb02ad8d0835ebc6ecb3e444`.
Статус: проект реализации и запуска; обучение в рамках подготовки ТЗ не запускалось.

## 1. Решение

Использовать уже подготовленный optimizer-ready bootstrap M137-5CH, сохранить практически весь Adam, собрать новый replay при komi=1.5, коротко адаптировать WDL/score и постепенно разморозить сеть. Базовый LR родителя равен **1e-4**, поэтому начальный LR trunk — **2e-6** (в 50 раз меньше), после прогрева — **5e-6…1e-5** (в 20–10 раз меньше). Не возвращаться автоматически к 1e-4.

Основа рекомендаций — приложенный `deep-research-report.md`: hybrid Adam, bridge, gradual unfreezing, контроль реальных обновлений и защита от забывания. Числа ниже — проверяемые инженерные стартовые настройки, а не гарантия сохранения силы или измеренный оптимум.

Поправки к общему отчёту для этой сети:

- Удаление канала уже сохраняет старую функцию: `W5=W6[:,:5]`, `b5=b6+0.5*W6[:,5]`. Дополнительный adapter не нужен. Это сохранение поведения сети при старом входном komi=0.5, а не адаптация к новому судейству 1.5.
- В сети LayerNorm, не BatchNorm. Перекалибровка BN не требуется.
- Семантика WDL остаётся победа/ничья/поражение, а score — итоговый margin; изменяются цели. Не сбрасывать Adam всех heads автоматически только из-за изменения komi. Сброс WDL/score — отдельный сравнительный эксперимент при доказанной нестабильности.
- Длинный bridge 500–2000 updates не брать без поправки на объём данных: у родителя было 160 updates на поколение. Начать с 160, продлевать только с новыми данными.
- Не делать плавный переход komi: 5ch-сеть не получает его на вход. Смешивание одинаковых наблюдений с целями разных komi создаёт конфликт. Весь новый training/self-play/eval contract фиксирует 1.5.

## 3. Обязательная поправка к reset bias и training clock

Текущий bootstrap сохраняет step=15520 при нулевых m/v bias. Это не обычный fresh Adam: при betas=(0.9,0.999) первый update при ненулевом градиенте и пренебрежимо малом eps будет примерно `3.16*LR`, а не `LR`; на следующих шагах множитель также может быть повышен. Низкий LR и clipping сами по себе не исправляют bias correction.

Предпочтительный контракт нового trainer:

1. Загрузить существующий bootstrap, сверить хеш и migration report.
2. Для одного `input_projection.bias` в новой производной ветке установить m=v=0, **локальный Adam step=0**. Сохранить отчёт этой поправки; исходный файл не менять.
3. Всем остальным параметрам сохранить m/v/step. Не обнулять heads по умолчанию.
4. Разделить `global_update_count` и per-parameter Adam step. Для frozen параметров использовать `requires_grad=False`, `grad=None`; не обновлять их моменты и счётчики.
5. При разморозке сохранять прежние состояния; новый LR задавать после загрузки optimizer. Хранить стабильные имена параметров в группах.

Существующие проверки `_adam_step()` требуют одинакового step у всех параметров. Их нельзя просто отключить: новый adapter должен проверять ожидаемый step каждого параметра на основе истории freeze/unfreeze и сохранённых начальных offsets. При падении/возобновлении состояние должно воспроизводиться.

Установка `lr=0` не эквивалентна заморозке optimizer: m/v и step могут продолжать меняться. В данном ТЗ замораживаются и веса, и их история оптимизации.

## 4. Данные до первого update

Фиксированный teacher/baseline — исходный M137-5CH bootstrap. Новые партии играются с настоящим referee komi=1.5. Сохранить исходные search settings, batch=64, loss weights и score normalization=81.5; не менять одновременно cpuct, temperature schedule, архитектуру и optimizer. Resign отключить на этапе bootstrap, чтобы получить формальные terminal labels.

Первичный буфер: ориентир 512 полных игр и минимум 50 тысяч валидных training-позиций; если позиций меньше — продолжить сбор. Это бюджетная стартовая величина, уточняемая по разнообразию/длине партий. Отделить примерно 10% игр в фиксированный validation corpus; игры, симметрии и связанные позиции одной игры не разделять между train и validation. Не переиспользовать validation в replay.

Для каждого sample сохранять game id, actor checkpoint, rules/komi/target fingerprints, 5ch observation, legal mask, MCTS visits, side-to-move, terminal outcome/ownership/score и происхождение. Начальные свежие данные — от frozen baseline, затем от принятого champion. Сохранять случайные seeds и распределение стартов; arena seeds отделить от training.

Старый replay при komi=0.5 в основной loss не включать. Простая замена value недостаточна: старые visits и продолжения партий сформированы другим поиском/целями. Допустимые отдельные режимы:

- Старые позиции как диагностический anchor set, без старых supervised targets.
- Позже reanalysis: восстановить полное состояние с историей, запустить поиск и новые продолжения при 1.5, записать новые targets и provenance. Это отдельная работа, не обязательная для запуска.
- Итоговый score старой завершённой партии можно пересчитать при новом komi, но он остаётся исходом старой траектории, а не новым on-policy target. Не объявлять такой relabel эквивалентом свежего replay.

Новый rolling replay наполнять до 6 поколений без наследования parent history. Начальный corpus удерживать на этапе адаптации; после накопления 6 новых поколений перейти к обычному окну. Сэмплировать по играм/фазам, не заполнять batch соседними ходами одной партии. Логировать долю свежих данных и распределение повторного использования.

## 5. Расписание первого пилота

Ниже steps — дополнительные optimizer updates после bootstrap, не поколения. Переходы разрешать только после validation/arena gates. При нехватке данных — собирать партии, а не повторять малый буфер тысячи раз.

| Фаза | Updates | Что обучается | LR |
|---|---:|---|---|
| Baseline | 0 | Только сбор/оценка | 0 |
| Bridge | 1–160 | WDL (`value_head`) и `score_head`; всё остальное frozen | Линейно 2e-6 → 1e-5 за первые 80, затем 1e-5 |
| Partial | 161–480 | + blocks 6–7, output_norm, policy/ownership heads; stem и blocks 0–5 frozen | Trunk/policy/ownership: 1e-6 → 2e-6 за 80; WDL/score: 1e-5 |
| Full low-LR | 481–1120 | Вся сеть | Stem/trunk/policy/ownership: 2e-6 → 5e-6 за 160; WDL/score: 1e-5; reset bias: 1e-6 → 5e-6 за 160 его активных updates |
| Stabilize | 1121–2400 | Вся сеть при успешных gates | Shared: 5e-6 → максимум 1e-5; WDL/score максимум 2e-5; рост только после принятого eval |

Bridge предназначен для адаптации предсказания исхода при новом судействе: первый слой уже сохраняет старую функцию, его не требуется срочно переучивать.

Оставить cadence максимум 160 updates между порциями нового self-play; первые контрольные сохранения на 40, 80, 160, затем каждые 160. Ограничить расход данных: первые фазы `updates*64/N_train <= 0.5` между обновлениями буфера, далее <=1.0 как стартовый guard. Для 160 updates нужно 10240 draws; при 50k позиций это ~0.205 прохода. По завершении пилота оценить результат, не выполнять безусловный LR jump.

## 6. Защита от забывания и наблюдаемость

Базовый loss оставить policy + WDL + ownership + score с исходными весами. Не distill старые WDL/score: они закрепят старое komi. Старый policy также не инвариантен к komi, поэтому сильный policy KL способен мешать правильной адаптации.

Первый кандидат: hybrid Adam + staged LR/freeze + слабый L2-SP для shared representation (stem, blocks, output_norm), без anchoring WDL/score. Определить L2-SP явно как средний квадрат отклонения shared weights от bootstrap. На pilot batches после начала разморозки подобрать коэффициент до ~5–10% нормы supervised gradient shared-группы; в точке старта L2-SP gradient равен нулю, поэтому калибровать на ней нельзя. Сохранить выбранный коэффициент, не пересчитывать его на каждом шаге. Ослаблять после успешных gates.

Teacher из приложенного отчёта полезен как дополнительная страховка при обнаруженном drift: слабое feature matching на новых позициях, с контролем градиентного вклада и отдельным сравнением. Не включать одновременно KD, EWC, новый optimizer и несколько неизвестных регуляризаций. EWC без заранее оценённой importance не нужен для первого запуска.

Gradient clipping: global norm 1.0 как стартовая настройка; записывать norm до clip и частоту clip. Если доступна надёжная историческая статистика, заменить порогом 1.5–2× исторического p95. При частом clip проверить масштабы losses; не повышать порог автоматически. Clipping не ограничивает непосредственно Adam update.

Логировать отдельно по группам: LR, grad norm, update norm, относительный update/weight norm, drift от bootstrap, диапазоны m/v, per-parameter step, freeze mask. Дополнительно: все четыре train/validation losses, WDL calibration/Brier, score MAE, policy entropy, pass rate, длины игр, invalid moves и non-finite. Для почти нулевых весов использовать также абсолютную норму update: относительная нестабильна.

## 7. Оценка силы и stop/promote

Основная оценка — candidate против фиксированного M137-5CH **при komi=1.5 у обоих**, с одинаковым числом MCTS simulations, фиксированными settings, noise off, resign off и парными стартами со сменой цветов. Разбить случайность training/eval; не выбирать checkpoint по validation loss одной головы. Диагностика при 0.5 допустима отдельно, но не обязана оставаться неизменной после адаптации к 1.5.

Быстрый screen после 160, 480, 1120 updates: 128 пар (256 игр). Это выявляет крупный провал, но не доказывает отсутствие регрессии в несколько процентов. Формальная проверка лучшего кандидата: не менее 512 пар (1024 игр); bootstrap CI по парам, score=W+0.5D, заранее заданный критерий.

- Promote только если нижняя граница 95% CI score против baseline >=0.47 (non-inferiority margin 3 п.п.), validation не деградирует и нет патологического поведения. Это допуск на регрессию, а не доказательство улучшения.
- Для утверждения улучшения нижняя граница CI должна быть >0.50.
- Если верхняя граница CI <0.47 — reject/rollback. Если интервал пересекает порог — результат неопределённый; добавить независимые пары, не объявлять успех.
- Частые промежуточные screens не использовать как многократный поиск статистической значимости. Финальную проверку провести на новых seeds после выбора кандидата.

Немедленно остановить при NaN/Inf, нарушении legality/target identity или целостности state. При двух validation ухудшениях подряд более 10% относительно лучшего принятого checkpoint по WDL/score и отсутствии выигрыша arena — остановить продвижение и проверить причину. Это стартовый operational threshold, не универсальная норма.

При аномальном update/weight spike относительно устойчивого участка (>5× медианы той же группы, с абсолютным контролем) приостановить run, проверить bias reset/LR load/freeze. Откатить **model + optimizer + scheduler + RNG + replay cursor/identity + phase counters**, уменьшить LR проблемной группы вдвое, повторить ограниченный pilot. Не восстанавливать только веса поверх уже ушедшего Adam.

Candidate не становится actor автоматически: до gate self-play производит последний принятый champion. Если кандидат отвергнут, replay от него не включать автоматически. Сохранять все actor identities.

## 8. Работы по коду и критерии приёмки

Текущая 5ch реализация маркирована inference-only. Run-owned trainer проверяет старый architecture id, единый LR и общий Adam step. Простого изменения JSON недостаточно.

1. Реализовать отдельный training adapter/контракт 5ch: observations [5,81], komi только в referee/targets/provenance; model factory, batched self-play inference, train, checkpoint load/save и eval поддерживают одну архитектуру. Подключить существующие new_komi guards к runtime, не только bootstrap tool.
2. Реализовать run-owned komi=1.5 во всех terminal targets: score Black margin уменьшается на 1 относительно 0.5, White увеличивается; WDL пересчитывается по новому referee. На фиксированном terminal board ownership не меняется. В реальных новых партиях распределение ownership может меняться. Normalization 81.5 оставить явно версионированной.
3. Добавить именованные optimizer groups, локальные clocks, freeze schedule, LR warmup и надёжное восстановление всех состояний. Исправить loader, который сейчас переустанавливает одинаковый LR всем группам.
4. Добавить fresh-only replay, validation split по играм, sample budget, опциональный L2-SP, диагностику обновлений, arena gating и rollback.
5. Сохранить FP64-аккумуляцию folded projection на первом этапе. Если понадобится FP32 ради скорости — отдельная численная/поведенческая проверка; не совмещать со сменой komi без оценки.
6. Создать новый immutable restart artifact/config от существующего bootstrap; отметить step-reset bias и выбранное komi. Флаг training_ready выдавать по результату проверки всей цепочки, а не ручной заменой false на true.

Обязательные тесты при реализации:

- Побитовое сохранение untouched optimizer states, точный crop, fresh bias step=0; все значения конечны, v>=0.
- Frozen weights/m/v/step не меняются; активные step растут; после unfreeze состояния восстанавливаются по именам.
- Resume на границе фаз даёт те же последующие LR/updates/weights в детерминированном CPU smoke, что непрерывный запуск.
- 5ch observations не зависят от komi; terminal score/WDL при 0.5 и 1.5 меняются корректно с обеих сторон, включая пограничные результаты.
- Старый replay отклоняется по contract fingerprint; validation games отсутствуют в training.
- LR из старого checkpoint не затирает schedule; rollback возвращает согласованный полный state.
- Короткий end-to-end smoke: self-play → targets → несколько updates → save/load → arena. Только после него долгий pilot.

## 9. Основания и границы выводов

Основной исследовательский материал: приложенный `deep-research-report.md`, особенно разделы о hybrid optimizer, reset step, progressive unfreezing и ограничениях distillation. Его универсальные советы адаптированы к проверенным локальным фактам; они не являются указанием запустить обучение.

Кодовые источники: `torus9_m137_5ch.py`, `torus9_new_komi.py`, `torus9_monolith.py`, `torus9_training.py`, `torus9_run_owned_training.py`; родительские checkpoint metadata и локальные бинарные артефакты.

Формула bias correction сверена с [официальной документацией PyTorch Adam](https://docs.pytorch.org/docs/main/generated/torch.optim.adam.Adam_class.html). Общая идея teacher без старых данных описана в [Learning without Forgetting](https://arxiv.org/abs/1606.09282); это не доказательство эффективности сильной дистилляции policy при смене komi.

Результаты arena нового обучения отсутствуют: LR, длительности, бюджеты и thresholds требуют проверки пилотом. Гарантировать отсутствие ухудшения заранее нельзя; цель протокола — ограничить изменение сети и не продвигать регрессирующий checkpoint.

## 10. Ключевые точки: отчёт, уведомление и решение пользователя

Уточнение пользователя: после каждого этапа нужен краткий отчёт и понятное следующее действие, чтобы пользователь мог вызвать Codex для разбора. Для первого пилота все переходы между этапами требуют явного решения; успешный численный gate означает допустимость перехода, но не запускает его автоматически. Это правило уточняет разделы 5 и 7.

### Точки остановки

1. Первичный replay собран: отчёт о числе игр/позиций, качестве targets, разделении train/validation и готовности к bridge.
2. Bridge завершён и арена на 256 игр закончена: отчёт о прогреве голов и допустимости частичной разморозки.
3. Partial завершён и арена на 256 игр закончена: отчёт о размороженных слоях и допустимости полной разморозки.
4. Full low-LR завершён и арена на 256 игр закончена: отчёт о стабильности всей сети и допустимости стабилизации.
5. Stabilize завершён и финальная арена на 1024 игры закончена: итог пилота и решение о дальнейшем обычном обучении.

После обучения внутри этапа арена запускается автоматически. Если арена или validation завершились ошибкой, отправить сообщение о сбое с имеющимися данными; не ждать успешной оценки бесконечно. Числа выше — игры, не пары.

### Порядок завершения этапа

Сначала сохранить полный checkpoint и проверяемые артефакты оценки, затем атомарно зафиксировать состояние `NEEDS_REVIEW` и отчёт, затем поставить уведомление в устойчивую очередь. Следующий этап не запускается до явного решения. Во время ожидания не производить дополнительные training/self-play updates; повторная доставка уведомлений разрешена.

Использовать существующую инфраструктуру `gocube_golden.notifications` и Telegram dispatcher оркестратора, с настроенным каналом пользователя. Не создавать параллельную систему отправки. Наличие инфраструктуры не означает, что уведомления этого нового workflow уже подключены.

### Содержание сообщения

- Run id, этап, статус: «этап завершён — ожидается решение», «ошибка» или «пилот завершён — ожидается решение».
- Что сделано: новые игры, позиции replay, updates на этапе и суммарно, trainable группы, фактический LR и время.
- Короткая оценка: validation до/после, arena W/D/L и score с 95% CI, opponent checkpoint, komi, simulations; обнаруженные отклонения. До первой арены явно писать «арена ещё не проводилась».
- Результат автоматических проверок: PASS / FAIL / INCONCLUSIVE. Не называть PASS доказательством улучшения.
- Полный путь к отчёту и checkpoint; пригодная ссылка только если настроен доступный пользователю просмотрщик. Локальный путь не выдавать за доступную с телефона веб-ссылку.
- Рекомендуемое действие и доступные альтернативы: продолжить следующий этап, расширить оценку, повторить от checkpoint с изменённым LR, завершить запуск. При FAIL продолжение блокируется до устранения причины.
- Готовый запрос для Codex с конкретными run id, stage id и абсолютным путём отчёта.

Пример сообщения (шаблон, не фактический результат):

```text
M137-5CH / komi=1.5 — этап 2/5 завершён
Сделано: 160 updates, обучались WDL/score, trunk заморожен.
Арена: 256 игр против исходного M137-5CH, 256 simulations.
Результат: <W/D/L>, score <...>, 95% CI <...>.
Проверки: <PASS/FAIL/INCONCLUSIVE>. Замечания: <...>.
Обучение приостановлено. Следующий этап: последние 2 блока + головы.
Рекомендация: <изучить отчёт и разрешить переход / расширить арену / ...>.
Отчёт: <абсолютный путь>/stage-02/report.md

Запрос для Codex:
«Разбери отчёт <абсолютный путь>/stage-02/report.md для run <id>,
проверь метрики и checkpoint. Порекомендуй продолжение, дополнительную
оценку или повтор с меньшим LR. До моего решения обучение не возобновляй».
```

### Надёжность и восстановление

- Сохранить `report.json` для машинной проверки и `report.md` для пользователя. Указать config/checkpoint/replay hashes, версию кода и ссылки на исходные метрики.
- Стабильный event id: run + stage + attempt + тип события. После рестарта не создавать новое логическое событие для того же завершения. При сетевой неоднозначности доставки возможен дубликат сообщения; event id позволяет его распознать.
- Ошибка доставки не снимает паузу и не теряет отчёт: сохраняются outbox, attempts, last_error и статус доставки; повтор с backoff.
- Экран/команда статуса показывает текущую фазу, прогресс игр/updates/арены, heartbeat, ETA с пометкой «оценка», причину паузы, путь к отчёту и статус уведомления.
- Решение пользователя сохранять с run/stage/attempt/checkpoint hash и выбранными параметрами. Повторная или устаревшая команда не должна запускать два процесса или продолжать другую попытку.
- После перезапуска в `NEEDS_REVIEW` сохранять паузу. Истечение времени, прочтение сообщения и появление Codex не являются разрешением продолжить.
- Дополнительно уведомлять об аварийной остановке внутри этапа. Не отправлять регулярные сообщения «всё ещё работает» без отдельного запроса.

Критерии приёмки: тесты каждого завершения и ошибки арены; падение между сохранением отчёта и отправкой; недоступный Telegram; повторная доставка/рестарт; отсутствие следующего этапа без решения; защита от повторного resume. Тесты отправки используют fake transport; реальный тест доставки выполняется отдельно при настройке запуска.

Статус этого раздела: требование внесено в ТЗ; runtime workflow и доставка этапных сообщений пока не реализованы и не активированы.

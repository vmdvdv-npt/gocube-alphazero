# ТЗ: корректность и геометрия адаптации KataGo для GoCube

Дата: 8 сентября 2026 года. Проверенная ревизия: `842de66323e1bd20caaac4cec3df007608190611`.

Статус: техническое задание на реализацию по запросу владельца проекта. S1 и S2 уже находятся в базовой ветке, а раздел S3 реализован в текущем изменении; остальные разделы остаются планом дальнейшей работы. Документ не меняет действующие правила продукта и не объявляет существующие результаты обучения недействительными без анализа конкретных данных.

## 1. Цель, границы и зафиксированные решения

Цель — устранить подтверждённые ошибки в обучающих результатах и использовании моделей, дать сети возможность различать существенные особенности куба и установить проверяемые критерии качества адаптации.

Решения владельца проекта, обязательные для всех работ по этому ТЗ:

| Параметр | Значение | Требование |
| --- | --- | --- |
| Коми | **0,5** | Зафиксировано владельцем по практике игры; не оптимизировать, не включать в sweep и не делать пересмотр условием приёмки |
| Обычный поиск self-play | **50 симуляций** | Сохранить |
| Быстрый поиск self-play | **20 симуляций** | Сохранить |
| Основная проверка силы в Arena | **50 симуляций** | Сохранить одинаковый бюджет у сравниваемых моделей |
| Основной объект | Cube 4, 96 точек | Приоритет реализации и экспериментов |
| Геометрический контракт | Текущие `PointId`, порядок действий и соседство | Не менять игровую модель ради удобства сети |

Для обоснования этих фиксированных настроек достаточно принятого решения проекта: данное ТЗ не требует отдельного доказательства баланса коми. Проверки 50/20 должны устанавливать соблюдение бюджета, а не искать ему замену.

Не входят в обязательный объём: увеличение числа симуляций, переход на другую систему правил, динамическое коми, полное воспроизведение всей архитектуры KataGo, переписывание UI, внедрение human-vs-AI, замена существующей инфраструктуры обучения.

Создание документа не означает разрешения автоматически прерывать текущие запуски, удалять replay/checkpoints или заменять используемую модель. Во время реализации старые артефакты сохраняются, несовместимые эксперименты получают отдельные пространства имён.

## 2. Оценка текущего состояния и реестр проблем

Основа проекта пригодна для дальнейшей работы: правила используют граф соседства; имеются pinned KataGo oracle, дифференциальные тесты, версии наблюдений и целей, проверки перспективы value, атомарные checkpoint/replay и восстановление обучения. Эти механизмы нужно сохранить.

Но утверждение «осталось исправить геометрию сети, всё остальное уже правильно адаптировано» не подтверждается. При дополнительной проверке найдены ошибки, отсутствующие в рассмотренных регрессионных тестах.

Приоритеты:

- **P0** — блокирует доверие к результатам затронутого пути либо использование актуальной модели.
- **P1** — требуется до приёмки новой адаптации; не всегда запрещает диагностические запуски старой версии.
- **P2** — измеряемое улучшение или локальное отклонение; не объявляется причиной слабой игры без эксперимента.

| ID | Приоритет | Статус доказательства | Проблема |
| --- | --- | --- | --- |
| S1 | P0 | Воспроизведена ошибка победителя относительно pinned oracle | Scorer выбирает разные алгоритмы по наличию `main_moves`; путь без ходов MAIN ошибается на проверенной позиции |
| S2 | P0 для интеграции | Воспроизведена ошибка загрузки настоящего временного checkpoint | Manifest и загрузчик разрешают базовый класс с 17 каналами вместо актуального pinned-класса с 18 |
| S3 | P1 | Подтверждено кодом и исполнением; частота в реальном обучении не измерена | Аварийный лимит принудительно оценивает позицию даже внутри search clone и теряет причину завершения |
| G1 | P1 | Доказано устройством сети и численным экспериментом | На пустом кубе все точки обязательно имеют одинаковый policy prior при любых весах |
| V1 | P1 | Установлена граница проверок | Прямоугольный oracle не доказывает корректность тактики в угловых треугольниках и на всей замкнутой поверхности |
| V2 | P1 для заявления о совместимости с продуктом | Подтверждено различие жизненных циклов; универсальное равенство результатов не доказано | Доигрывание обучения и assisted/manual review продукта не имеют достаточной проверки соответствия |
| H1 | P1, аудит | Требует анализа достижимости и пар состояний | Полнота наблюдения относительно истории, стартов доигрывания и правил завершения |
| M1 | P2 | Воспроизведён ложноположительный признак ко | `_simple_ko_likely_active` считает любое изменение двух точек вероятным ко |
| N1 | P2 | Архитектурное ограничение установлено; эффект на силу не измерен | Нет отдельной передачи глобального контекста в локальные головы; score не моделирует неопределённость |

P0 S1 относится к затронутым setup/cleanup-путям. Из найденного примера не следует, что все обычные партии из пустой позиции получают ошибочный результат. P0 S2 блокирует путь checkpoint → integration service; это не доказательство поломки встроенной Arena, использующей уже разрешённый класс игры.

## 3. S1 — единый корректный подсчёт и инициализация доигрывания

### 3.1. Подтверждённый дефект

Файл `alphazero/envs/gocube/katago_v3.py`, функция `final_v3_score`:

```python
has_move_history = bool(any(state.main_moves))
life = (
    independent_life_analysis(board, topology)
    if has_move_history
    else _legacy_board_only_life_analysis(board, topology)
)
```

Нулевой счётчик ходов MAIN не является надёжным признаком «это только старая тестовая позиция». `rebase_cleanup_training_state` в `selfplay_semantics.py` обнуляет `main_moves` у настоящих стартов обучающего доигрывания. После перехода в cleanup этот счётчик уже не увеличивается.

Контрпример на поддерживаемой test-only прямоугольной топологии 5×5:

- Индекс точки: `y * 5 + x`.
- Пустые точки: 6 `(1,1)` и 18 `(3,3)`.
- Белый камень: 7 `(2,1)`.
- Все остальные точки заняты чёрными, ход чёрных, коми 0,5.
- Из одинакового setup обе реализации выполняют шесть PASS.
- Наш результат `White − Black = +0,5`, победитель White.
- Pinned KataGo: `White − Black = −3,5`, победитель Black.

У белого камня есть свобода; пример не опирается на оставленный на доске камень с нулём свобод. Дополнительно воспроизведён тот же локальный результат после `rebase_cleanup_training_state(..., CLEANUP_2)` и двух PASS. Прямой phase-2 reset самого oracle в этой проверке не выполнялся: его нужно добавить в рамках реализации.

### 3.2. Требуемая реализация

1. Убрать выбор производственного scorer по `bool(main_moves)`. Одна версия правил должна иметь одну определённую семантику подсчёта для ordinary games, setup и synthetic cleanup.
2. Выделить явный контракт инициализации счёта для позиции, созданной не с пустой доски. Он должен учитывать начальные камни, captures, фазу и стартовые цвета второй cleanup-фазы.
3. Сопоставить этот контракт с `BoardHistory::clear` pinned KataGo. В upstream инициализируется `whiteBonusScore` с учётом камней и captures; простого удаления ветки `else` недостаточно.
4. Если старым fixtures нужен исторический helper, вынести его из производственного пути и явно назвать legacy. Обучение, поиск и обычный V3 scorer не должны выбирать его неявно.
5. Расширить C++ oracle adapter для явного начального encore phase и, при необходимости, captures. Adapter только задаёт состояние и вызывает native API, не вычисляет ожидаемый ответ Python-кодом.
6. Проверять все производные результата: победителя, разность счёта, формальные области, ownership, маски, диагностический breakdown. Равенства только `winner` недостаточно.
7. Установить согласованный смысл абсолютных `score.black/white`. Если внутренний эквивалентный area-подсчёт даёт общую добавку обеим сторонам, не выдавать эти числа как пользовательский breakdown территории и пленных без преобразования.

### 3.3. Приёмка

- Контрпример выше проходит относительно native oracle с результатом `−3,5`.
- Differential suite покрывает setup в MAIN, CLEANUP_1 и CLEANUP_2; ноль реальных MAIN-ходов больше не переключает правила.
- Проверены pass-only продолжения, реальный capture, PASS-for-ko и переход между cleanup-фазами после каждого вида старта.
- Cube-позиции с intruder внутри pass-alive области проходят независимую графовую проверку; прямоугольный oracle не объявляется эталоном всего куба.
- Для семантически одинакового состояния, полученного replay либо разрешённой реконструкцией, совпадают score, ownership и законные продолжения. Сравнение допускается только после корректного восстановления всего score-relevant состояния.
- Изменение правил подсчёта получает новую implementation/target-версию. Старый replay не загружается под новым смыслом без явной миграции.

### 3.4. Проверка накопленных данных

Определить затронутые игры по типу старта и истории. Сохранить число проверенных игр, долю изменённых победителей, распределение разницы score и число изменённых ownership labels.

Если в записи недостаточно истории для точной реконструкции, это отдельная категория `not_reconstructible`, а не предположение «скорее всего всё правильно». Не смешивать такие данные с исправленным replay. Не удалять исходные файлы.

## 4. S2 — единый контракт модели от обучения до GoCube

### 4.1. Подтверждённый дефект

Актуальный класс обучения: `DiversifiedPinnedCube4JapaneseGame`, observation shape `(18, 96, 1)`, schema `gocube-observation-v4-pass-would-end-phase`.

`ensure_training_manifest` передаёт в `RunManifest.create` только topology/size/rules/adjudicator. Там повторно выбирается базовый класс, и integration manifest получает `gocube-observation-v3`.

`CheckpointModelLoader.load` также вызывает базовый `game_class(...)`. При загрузке настоящего checkpoint, созданного актуальным training builder, получено:

```text
CheckpointLoadFailed:
Checkpoint GoCube contract mismatch for gocube_observation_schema:
saved='gocube-observation-v4-pass-would-end-phase',
expected='gocube-observation-v3'
```

Аналогичный способ разрешения класса имеется в `integration/generation.py` и части evaluation entrypoints. Их нужно проверить как одну цепочку. Приведённое воспроизведение непосредственно доказывает дефект integration loader, а не каждого CLI по отдельности.

### 4.2. Требуемая реализация

1. Ввести один resolver игрового/нейросетевого контракта по полным metadata: rules implementation, observation schema, action schema, topology identity, network architecture и search contract.
2. Создавать manifest из фактически используемого класса и effective args. Не восстанавливать его частичную семантику повторным выбором по topology/size.
3. Передавать один разрешённый контракт в создание сети, загрузку checkpoint, построение observation, генерацию партии и standalone evaluation.
4. Различать среду inference и curriculum-механику: inference не обязан генерировать synthetic forks, но обязан совпадать по observation, правилам и поисковой семантике.
5. Согласовать компактный `gocube-run.json`, богатый `run-manifest.json`, `effective-config.json` и checkpoint args. Конфликт не должен скрываться выбором удобного файла.
6. Сохранять строгую проверку несовместимости. Запрещено исправлять ошибку добавлением фиктивного канала, игнорированием fingerprint или `strict=False` при загрузке весов.
7. Добавить fingerprint канонического порядка точек и таблицы соседей. Текущий rules fingerprint содержит kind/size/count, но не непосредственно adjacency; изменение соседства при прежних размерах не должно оставаться незамеченным.
8. Старые модели остаются читаемыми только под их реальной исторической семантикой. Несовместимый manifest мигрируется отдельной явной операцией с сохранением исходника; массовое переименование версии не является миграцией.

### 4.3. Приёмка

Нужен интеграционный тест без подмены `NNetWrapper.from_checkpoint`:

```text
build_hardened_training_args
→ сохранение настоящего временного checkpoint и manifests
→ CheckpointCatalog
→ CheckpointModelLoader
→ predict_for_search
→ GameGenerator / service
→ законная последовательность действий
```

Проверить все четыре NN-head, форму observation и одинаковые результаты inference до/после загрузки. Проверить обе стороны партии и оба пути — прямой service и standalone evaluation. Для короткого CI fixture можно использовать небольшой тестовый бюджет, но не изменять production 50/20.

Негативные проверки: неверная топология, переставленные точки, изменённая adjacency, старая observation schema и несовместимые targets отклоняются с понятной причиной.

## 5. S3 — отделить лимит запуска от формальных правил

### 5.1. Подтверждённое поведение до S3 (historical)

До S3 базовый `apply_v3_action` при `256 + 24 * point_count` действиях создавал `NO_RESULT` с причиной `move-cap`. Pinned wrapper преобразовывал его в `SCORED`, очищая причину. Условие применялось также к search clones. Это больше не является актуальным контрактом.

Для Cube 4 лимит равен 2560. Историческая репродукция: clone принятого тестового состояния с `turns=2559` после следующего хода получал `SCORED`, причина отсутствовала. Наблюдение такого тестового состояния совпадало с наблюдением пустого состояния с `turns=0`, поскольку turn budget не кодировался. Этот искусственный пример показывал зависимость от скрытого поля; он не доказывал достижимость именно пустой доски после 2559 легальных ходов.

В upstream принудительный подсчёт после ограничения числа ходов расположен в game runner (`cpp/program/play.cpp`). Перенос этого ограничения в каждую ветвь поискового дерева требует отдельного обоснования; совпадение названия с KataGo его не заменяет.

Кроме того, описание «cap всегда означает только NO_RESULT» в части документов уже не соответствует pinned wrapper. Предыдущую оценку, основанную на этом описании, нельзя переносить на весь актуальный training path.

### 5.2. Реализация S3

1. Формальный `apply_v3_action` больше не применяет episode budget.
2. Лимит длины self-play реализован в episode runner. Pinned runner force-scores текущую позицию на уровне реального эпизода, не создавая terminal внутри MCTS по его номеру хода.
3. Предусмотреть отдельный технический предел поиска, если он необходим для гарантии завершения. Такой предел должен иметь собственную семантику и не выдавать техническую остановку за доказанную победу.
4. Сохранять `termination_reason` (`formal_pass`, `pass_alive`, `cycle`, `episode_move_limit`) и provenance результата/целей (`formal`, `rule_no_result`, `runtime`).
5. Не менять подтверждённое поведение настоящих циклов `NO_RESULT` и маскирование auxiliary targets.
6. Посчитать частоту episode limit по ordinary, synthetic cleanup и fork-играм; показать отдельно от естественных завершений.

### 5.3. Приёмка

- Search clone не получает ложный выигрыш только из-за приближения реального эпизода к лимиту runner.
- Достижение лимита эпизода воспроизводимо и имеет явную причину в записях и агрегатах.
- Тип цели выбирается по документированному контракту; техническую остановку не переименовывают молча в `NO_RESULT` или обычный финал.
- Переход к новому поведению версионирован. Для качества новой модели отдельно сообщается частота технических завершений.

S3 compatibility IDs: search contract `katago-pinned-search-v3`, game record
schema v3, replay format v3, training contract v3, and termination contract
`gocube-termination-provenance-v1`. Replay/training remain at S1's numeric v3
because the seven-tensor layout and optimizer/sample semantics are unchanged;
the new marker/checkpoint fields are required and therefore fail closed.
Existing records/replay/checkpoints are not rewritten; artifacts that lack the
new immutable contract are rejected by the current resume/load path or
classified as `unknown_legacy_termination` by the read-only record audit.

## 6. G1 — представление геометрии куба в нейросети

### 6.1. Что сохранить

Текущий куб — граф из `6N²` точек, а не сетка с объединёнными физическими вершинами. Каждая точка имеет четыре соседа. Восемь физических вершин образуют восемь треугольников соседства; при N=4 в них участвуют 24 точки. Нельзя заменять их восьмью узлами степени 3: это была бы другая игра.

Рёбра между гранями не являются краями доски. Точки по разные стороны шва взаимодействуют как обычные соседи. Координаты renderer, ориентация камеры и развёртка не входят в правила.

Проверенный пример: два чёрных камня `front:0:0` и `left:0:3` на иначе пустом Cube 4 имеют пять уникальных свобод, а `front:1:1` и `front:1:2` — шесть.

### 6.2. Почему текущего message passing недостаточно

`GraphMessageLayer` вычисляет линейную функцию собственного embedding и среднего embeddings соседей. На пустой доске все входы одинаковы; степень всех узлов равна 4. Поэтому на каждом слое embeddings остаются одинаковыми при любых весах. Это сохраняется при любой глубине сети данного типа.

Численный эксперимент на seed 0, 1 и 42 подтвердил нулевой разброс point-policy на пустом Cube 4. Ограничение относится к NN prior; MCTS и сеть на непустой позиции не обязаны выдавать одинаковые оценки.

### 6.3. Минимальная обязательная реализация

1. Предвычислять структурные признаки из adjacency, независимо от renderer:
   - число треугольников, содержащих точку, либо соответствующую бинарную маску;
   - кратчайшее расстояние до множества точек этих треугольников.
2. Определить точную нормализацию и schema. Для расстояния допустимо деление на `max(1, max_distance)`; для топологии без треугольников использовать явно определённое нулевое значение и нулевую triangle mask.
3. Подавать признаки в `input_linear` вместе с динамическими признаками либо через отдельную структурную проекцию. Способ отражается в architecture/observation metadata.
4. Сохранять общий набор весов между точками. Не вводить независимый обучаемый bias на каждый `PointId`, чтобы произвольная нумерация не подменяла геометрию.
5. Геометрические признаки сообщают структуру, но не задают, где «надо» играть. Не размечать вершины как хорошие ходы вручную.
6. Сначала сравнить минимальное расширение с исходной сетью. Более сложные distance profiles, edge features или другая GNN разрешаются только после измерения оставшихся ограничений.

### 6.4. Симметрии и обязательные проверки

- Для всех 24 пространственных вращений куба построить точные перестановки `PointId` и проверить сохранение adjacency. Если поддерживаются отражения, проверить весь выбранный набор отдельно.
- Структурные признаки при перестановке должны переноситься вместе с точками. Policy и ownership переставляются так же; value, score и PASS остаются инвариантны с точностью вычислений.
- Полная перестановка состояния включает previous board, ko masks, start colors, действия и релевантную историю, а не только текущие камни.
- Для пустого Cube 4 сеть должна быть способна различать разные структурные типы, сохраняя равенство внутри симметрической орбиты. Не требовать разницы для любых случайных весов — проверять возможность представить различие конструктивно или небольшой контролируемой задачей.
- Отдельная диагностическая задача: отличить принадлежность угловому треугольнику по входу сети; для новой архитектуры требовать 100% классификации 96 точек в фиксированном воспроизводимом эксперименте. Это проверка выразительности, а не оценка силы игры.
- На пустом торе пространственная однородность сохраняется. Отсутствие synthetic symmetry augmentation само по себе не считается дефектом: текущая GNN уже обладает соответствующей эквивариантностью.
- Проверить shapes и геометрию для всех заявленных размеров Cube 2–7. Отдельный короткий smoke для поддерживаемых размеров тора.

### 6.5. Миграция

Новые признаки несовместимы со старыми входными весами и replay observations. Новая schema и architecture ID обязательны.

Контрольный эксперимент — обучение с нуля. Продолжение старой модели возможно только как отдельно обозначенный transfer experiment: общие веса переносятся явно, новые каналы инициализируются по зафиксированному правилу, свежая модель не выдаётся за точное resume.

Replay можно дополнить только детерминированными структурными каналами, если остальные правила и targets неизменны. После S1 это условие для старого replay нельзя предполагать автоматически.

## 7. H1 и M1 — состояние, история и точность вспомогательных признаков

### 7.1. Аудит наблюдения

Составить таблицу всех полей `V3State` и pinned wrapper с колонками: влияет на legality / phase / score / root pruning / technical stop; как представлено в observation; можно ли точно восстановить из других признаков; как переносится в clone и replay.

Обязательно рассмотреть `main_moves`, `cleanup1_moves`, `cleanup2_moves`, captures, phase-local history, same-player pass states, ko capture history, second-cleanup start colors и remaining technical budget, если последний останется частью среды.

Отсутствие поля в observation не является автоматически ошибкой. Некоторые счётчики выводимы из occupancy/captures; требовать отдельный канал только для недостающей семантики. Ограниченное представление полной истории может быть осознанным приближением NN, если точный движок и поиск сохраняют эту историю.

Приёмка:

- Найдены либо опровергнуты достижимые пары состояний с одинаковым observation, но различной непосредственной legality, фазой после PASS или score offset.
- Подтверждённые неоднозначности устраняются точными масками/глобальными признаками либо явно выделяются как исследовательское ограничение с тестом. Не заявлять полную марковость без доказательства.
- Маски не включают знание будущего финала; обучение и inference строят их одинаково.
- Проверены ordinary start, early/ordinary fork, seki fork, synthetic cleanup, clone, сериализация и восстановление.

### 7.2. Ложноположительное ко в ending bonus

`_simple_ko_likely_active` в `alphazero/search_contract.py` проверяет только число изменившихся точек: `== 2`. Однокаменное взятие не обязательно создаёт simple ko.

Воспроизводимый пример Cube 4: чёрные `front:0:1`, `front:1:0`, `front:1:2`, `front:2:0`; белый `front:1:1`; ход чёрных в `front:2:1`. Эвристика возвращает True, хотя попытка белых восстановить позицию в `front:1:1` отвергается как suicide.

Требование: использовать точный признак simple ko из rule transition либо точную проверку восстановления предыдущей раскраски. Сохранить графовую независимость и не считать два изменённых пункта достаточным доказательством.

Приёмка: обычное однокаменное взятие из примера не отключает ending bonus как ко; реальное simple ko отключает соответствующую ветку; cleanup PASS-for-ko не путается с обычным взятием. Дополнительно сравнить root heuristics с native реализацией на применимых прямоугольных fixtures.

## 8. V1 и V2 — проверяемая тактика куба и соответствие продукту

### 8.1. Три уровня проверки

1. **Прямоугольный differential:** тот же setup и действия передаются native KataGo и локальному движку. Это эталон переноса выбранных upstream-правил на square grid.
2. **Графовая проверка куба:** независимое от производственных helpers вычисление групп, уникальных свобод, взятий, областей и ограниченных тактических продолжений.
3. **Продуктовая проверка:** одинаковая основная последовательность действий проходит TypeScript `GameEngine`; завершение сравнивается с проектной классификацией и scorer в пределах явно определённой применимости.

Нельзя объявлять проверку независимой, если она вызывает тот же `pass_alive_analysis` или `final_v3_score`, который проверяется. Нельзя применять square-grid oracle к угловому треугольнику через развёртку: такой треугольник не становится квадратной сеткой.

### 8.2. Обязательный корпус

| Семейство | Что должно быть установлено |
| --- | --- |
| Один камень и группы у вершины | 4 соседа, уникальные свободы, общие соседи, корректное соединение через три грани |
| Взятия у вершины | Capture-before-suicide, несколько соседних групп, отсутствие двойного счёта одной группы |
| Глаза | Два независимых глаза, один глаз, ложные глаза, объединение пустых областей через третью грань |
| Seki и dame | Нейтральные области, общий внешний путь, отсутствие territory в принятой Tax=SEKI семантике |
| Ko | Настоящее и ложное simple ko возле вершины, оба cleanup PASS-for-ko, цикл с полным контекстом |
| Локальная борьба через шов | Одинаковая тактика внутри грани и на локально эквивалентном участке шва |
| Глобальная связность | Пути через несколько граней, обход окружения, две компоненты после удаления группы |
| Доигрывание | Нулевой MAIN, оба synthetic старта, real cleanup moves и pass-only завершения |
| Раннее завершение | Pass-alive auto-end и ручное завершение при одинаковой формальной предпосылке |

На каждое семейство нужны положительные и отрицательные случаи; это не требование одного универсального ожидаемого хода. Для тактического решения допускается множество равноценных действий.

Для маленьких задач использовать полный перебор продолжений с точными правилами повторения и фиксированным внешним контекстом. При исчерпании ресурса результат — `unknown`, а не «мёртв», «жив» или «ничья». Доказательство в локальном подграфе без учёта внешних свобод не принимается за доказательство на кубе.

Сохранять происхождение fixture, seed/действия, внешние условия, ожидаемые инварианты и способ получения ответа. Метаморфные проверки выполнять на всех вращениях. Holdout отделять по исходной задаче/траектории до генерации её симметрий.

### 8.3. Граница с продуктом GoCube

Каноническое поведение продукта: два PASS → assisted/manual endgame review → полная классификация → подсчёт. Обучение использует игровые cleanup-фазы. Integration replay сейчас скрывает cleanup-действия.

Требования:

- Подтвердить равенство основных действий, captures и позиции после второго PASS через реальный TypeScript engine.
- Для позиций с независимо подтверждённой классификацией сравнивать результат продукта с корректно завершённым training cleanup.
- Различать ошибку scorer, ошибку игры слабой модели в cleanup и допустимое расхождение формальных систем. Победа в неидеально сыгранном cleanup не является доказательством истинного статуса исходной группы.
- Не требовать совпадения с произвольным ручным решением пользователя: manual override остаётся возможностью продукта.
- Хранить основную позицию и полный внутренний cleanup record для диагностики. UI может продолжать показывать только основную партию, но результат обучения должен быть воспроизводим из внутренней записи.
- Не превращать внешний AI в authoritative владельца `GameState` и не обходить manual review.

Результат этапа: матрица применимости и список минимальных контрпримеров. Неустранённые расхождения перечисляются явно; заявление «полностью совместимо с GoCube» до этого не допускается.

## 9. N1 — архитектурные улучшения после исправления корректности

### 9.1. Глобальный контекст

Сейчас mean pooling питает value/score/PASS, а point-policy и ownership вычисляются из локальных embeddings. В 6 residual blocks находятся 12 message-passing слоёв. Для Cube 4 измеренный диаметр графа равен 11: нельзя утверждать, что текущая глубина вообще не достигает противоположной стороны Cube 4. Для больших заявленных топологий предел радиуса уже требует отдельного анализа.

Экспериментальный вариант: вычислять инвариантный глобальный контекст из node embeddings и возвращать его всем точкам через общую проекцию до локальных голов либо внутри одного/нескольких блоков. Зафиксировать место, размер проекции и статистики pooling.

Проверки: вращения сохраняют эквивариантность; изменение удалённой позиции может менять относительные logits локальных альтернатив через контекст; стоимость inference измерена на штатных batches. Просто изменение общей нормировки softmax не считается передачей контекста в относительный выбор двух ходов.

### 9.2. Score uncertainty и насыщение

Текущий scalar score + zero-stdev utility — задокументированное приближение. Не объявлять его срочным дефектом только потому, что KataGo имеет более богатые головы.

Сначала измерить signed score error, calibration и долю clipped targets, отдельно по фазам и типам завершения. При необходимости сравнить с распределением score или mean/variance-head. Нельзя подставлять произвольную константу вместо обученной неопределённости.

Новый вариант обязан иметь точные target/loss/inference/search contracts и тест согласованности знака. Его включение в основную модель требует выигрыша по критериям раздела 10, а не только меньшего собственного loss.

Дополнительные liberty/group features допустимы как отдельный эксперимент после независимой проверки вычисления. Планарные ladder-эвристики автоматически не переносить: их применимость к вершинам и замкнутым путям должна быть доказана.

## 10. Экспериментальный протокол и критерии качества

### 10.1. Варианты и неизменные условия

После S1–S3 зафиксировать исправленный baseline:

- **B0:** исправленные правила/интеграция, исходная архитектура.
- **B1:** B0 + минимальные структурные признаки G1.
- **B2:** B1 + глобальный контекст, если эксперимент N1 выполняется.
- **B3:** дополнительная score uncertainty, только отдельным сравнением.

Не сравнивать архитектуры на разных версиях scorer и не приписывать архитектуре улучшение, вызванное исправлением ошибочных labels. Старые checkpoints полезны как исторические соперники только при совместимой игровой семантике.

Коми 0,5 и поиски 50/20 неизменны. Остальные настройки, кроме исследуемого изменения, фиксируются в effective config: fast fraction, noise, temperature, replay window, optimizer, sample clock, curriculum. Фактические параметры берутся из запуска, не из устаревших описаний: в репозитории встречаются разные defaults train batch size.

### 10.2. Два вида сравнения бюджета

1. Равное число новых self-play samples и одинаковый optimizer/sample ratio — проверка эффективности обучения по данным.
2. Равное фактически измеренное время/compute на одном оборудовании — проверка практической стоимости улучшения.

Более медленная архитектура не получает автоматически дополнительный compute в сравнении «за одинаковое время». Бюджет симуляций при этом остаётся 50/20.

### 10.3. Оценка силы

- Не менее трёх независимых training seeds для заключения об архитектуре. Парные варианты используют один набор seed и одинаковые стартовые правила.
- Фиксированный набор соперников и checkpoint-версия для всех сравнений; не только «новая против предыдущей».
- Парные игры со сменой цветов и разнообразными законными стартами. Повторение одной детерминированной партии сотни раз не увеличивает независимую выборку.
- Рекомендуемый стартовый объём — 128 пар позиций на соперника и seed. Это объём сбора, а не гарантия статистической достаточности.
- Arena: 50 симуляций, без root noise, одинаковый детерминированный режим выбора у обеих сторон. Источник разнообразия стартов фиксируется заранее.
- Отдельно показывать результаты по цветам, обычным стартам, вершинам, швам, cleanup, циклам и техническим завершениям.
- Считать доверительные интервалы с учётом пар и общих источников openings; не трактовать вращения одного fixture как независимые партии.

### 10.4. Приёмка архитектуры

Обязательные условия B1:

1. Все correctness/integration gates пройдены, новые structural features действительно доступны сети.
2. Holdout-тактика не содержит новых нарушений формальных правил; ошибки выбора хода сообщаются отдельно от ошибок движка.
3. Для основного заранее выбранного сравнения нижняя граница 95% интервала разности результативности относительно B0 выше нуля либо результат признаётся неубедительным и модель не объявляется сильнее.
4. Нет скрытого роста `episode_move_limit`/`NO_RESULT`, маскирующего оценку силы: доли и интервалы опубликованы вместе с результатами. Допустимый порог изменения фиксируется до эксперимента по baseline, а не после просмотра результата.
5. Приведены оба бюджета — sample и compute — и стоимость inference.

Успешное устранение ограничения выразительности не гарантирует немедленный рост силы. Если B1 не выигрывает, архитектурная способность считается исправленной, а гипотеза об улучшении обучения остаётся неподтверждённой.

## 11. Порядок реализации и завершение работ

| Этап | Изменения | Условие завершения |
| --- | --- | --- |
| 0 | Зафиксировать ревизии, добавить воспроизведения S1/S2, сохранить baseline metadata | Дефекты воспроизводятся без изменения существующих запусков |
| 1 | S1: scorer, score initialization, native setup/encore oracle, targets | Контрпример и расширенный differential зелёные; миграция данных определена |
| 2 | S2: resolver, manifest, loader, generator, evaluation | Настоящий актуальный checkpoint проходит весь integration path |
| 3 | S3 + H1 + M1: termination provenance, search boundary, state audit, точное ко | История/лимиты не создают необъяснимые labels; контракты версионированы |
| 4 | G1: structural features и симметрии | Проверены геометрия, выразительность, старые/новые schemas |
| 5 | V1/V2: кубический корпус и продуктовая граница | Есть независимые ответы и явная матрица применимости |
| 6 | B0/B1, затем при необходимости N1 | Получены воспроизводимые результаты при фиксированных 0,5 и 50/20 |

Работы можно разбивать на небольшие PR по этим границам. Исправление loader не должно ждать обучения новой архитектуры; исправление scorer не должно объединяться с подбором параметров сети. Оценка B0/B1 начинается только после фиксации одинаковых корректных labels.

В каждом PR указать: проблему, воспроизведение до исправления, итоговую семантику, затронутые contracts, тесты, ограничения совместимости и состояние старых артефактов.

После изменений обновить соответствующие существующие документы, прежде всего `KATAGO_JAPANESE_V3.md`, `KATAGO_PINNED_SEARCH.md`, `TRAINING_LOOP_CONTRACT.md`, `PRODUCTION_TRAINING_HARDENING.md` и integration documentation. Не оставлять одновременно нормативные утверждения «cap только NO_RESULT» и реализацию silent force-score. Исторические версии обозначать как исторические.

Финальная приёмка ТЗ требует не только зелёных тестов: нужны исправленные S1/S2, разрешённая семантика S3, работающий G1, воспроизводимая продуктовая граница и честный результат эксперимента. Неподтверждённый рост силы допустим как исследовательский итог, но не как основание объявить модель сильнее.

### 12.2. Воспроизведение S1

Запуск из корня репозитория. Скрипт использует существующий локальный native oracle; helper при необходимости собирает его из закреплённого исходника.

```bash
PYTHONPATH=tests:. .venv/bin/python - <<'PY'
from gocube_reference_topology import rectangular_test_topology
from katago_reference_runner import KatagoOracleProcess
from alphazero.envs.gocube.katago_v3 import (
    v3_state_from_board, apply_v3_action, terminal_from_state,
)

t = rectangular_test_topology(5, 5)
black = [p for p in range(25) if p not in (6, 7, 18)]
white = [7]
state = v3_state_from_board(t, black=black, white=white)
for _ in range(6):
    state = apply_v3_action(state, t.pass_action, t)
terminal = terminal_from_state(state, t, 0.5)
local_score = terminal.score.white - terminal.score.black
with KatagoOracleProcess(x_size=5, y_size=5) as oracle:
    oracle.setup({
        'black': [[p % 5, p // 5] for p in black],
        'white': [[p % 5, p // 5] for p in white],
    })
    for _ in range(6):
        reference = oracle.play('pass')
print('local W-B:', local_score)
print('KataGo W-B:', reference['final_score'])
assert local_score == reference['final_score']
PY
```

На проверенной ревизии последняя строка должна падать: `0.5 != -3.5`. После исправления обе величины должны равняться `−3,5`. В постоянном regression-тесте нужно также проверять phases, legality и terminal kind до сравнения score.

### 12.3. Воспроизведение S2 без изменения пользовательских checkpoints

Скрипт создаёт случайно инициализированную сеть с настоящим актуальным контрактом; обучение не запускается. Файлы находятся в автоматически удаляемом временном каталоге. Использование обычного `NNetWrapper` здесь достаточно: дефект находится на границе schema/manifest, а не в атомарной записи hardened wrapper.

```bash
.venv/bin/python - <<'PY'
import tempfile
from pathlib import Path
from alphazero.NNetWrapper import NNetWrapper
from alphazero.envs.gocube.katago_train import (
    build_katago_training_args, parse_args,
)
from alphazero.envs.gocube.integration.catalog import CheckpointDescriptor
from alphazero.envs.gocube.integration.manifest import ensure_training_manifest
from alphazero.envs.gocube.integration.models import CheckpointModelLoader

game_cls, args = build_katago_training_args(parse_args([]))
args.cuda = False
with tempfile.TemporaryDirectory(prefix='gocube-audit-') as folder:
    model = NNetWrapper(game_cls, args)
    model.save_checkpoint(folder=folder, filename='iteration-0000.pkl')
    manifest = ensure_training_manifest(folder, 'audit', game_cls)
    print('checkpoint schema:', game_cls.OBSERVATION_SCHEMA)
    print('manifest schema:', manifest.observation_schema)
    item = CheckpointDescriptor(
        checkpoint_id='audit@0', run_name='audit', iteration=0,
        topology='cube', size=4, rule_set='japanese', komi=0.5,
        terminal_adjudicator=game_cls.TERMINAL_ADJUDICATOR_ID,
        path=str(Path(folder) / 'iteration-0000.pkl'),
    )
    class Catalog:
        def get(self, checkpoint_id):
            return item if checkpoint_id == 'audit@0' else None
    CheckpointModelLoader(Catalog(), device='cpu').load('audit@0')
PY
```

На проверенной ревизии последний вызов завершается `CheckpointLoadFailed` из-за несовпадения observation schema. Постоянный тест после исправления должен использовать реальный catalog и production manifest/loader, а затем сделать inference и короткую генерацию; минимальный probe выше изолирует уже найденную ошибку.
